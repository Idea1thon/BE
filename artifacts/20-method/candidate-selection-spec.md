## 0. 데이터 준비 (결합 규칙)

후보 선정은 정규화된 feature table 위에서만 수행한다. 원천 CSV를 직접 조인하지 않는다. 아래 7개 규칙은 2026-09-01 정합성 검사에서 확정됐다.

### 0-1. 분기–파일 1:1 배정 (H1)

점포·추정매출은 연도 폴더가 20251~20254를 중복 수록한다. 병합 시 분기를 파일 하나에만 배정한다.

- `점포/2021년~2025년/`, `추정매출/2021~2025/` = 해당 연도 분기(≤20254) 담당
- `점포/2026년/*.csv`, `추정매출/2026/*.csv` = **20261만** 로드, 20251~20254 행은 제외
- 예외: 추정매출 배후지는 2025 폴더에 정상 파일이 없어(0-4 참조) 2026 파일이 20251~20261 단독 커버
- 병합 후 `(기준_년분기_코드 + 공간코드 + 서비스_업종_코드)` 키 중복률을 로그로 남긴다. 중복 0이 아니면 feature table 빌드 실패로 처리한다.

### 0-2. 로드 파이프라인 순서

`위치 기반 읽기 → 컬럼 rename → grain 판정 → 표준 키 부여 → 분기-파일 배정 → 병합`

컬럼은 header 이름을 신뢰하지 않고 위치로 읽은 뒤 rename한다. rename 사전은 세 묶음:

- `ENG2KOR`: 2025년 영문 헤더 3파일 (`stdr_yyqu_cd→기준_년분기_코드`, `trdar_cd→상권_코드`, `stor_co→점포_수`, `thsmon_selng_amt→당월_매출_금액` 등) — `scripts/audit_data_integrity.py` 참조 (H3)
- 추정매출 건수 블록: `시간대_건수~06_매출_건수 → 시간대_00~06_매출_건수` (06/11/14/17/21/24 전부) (M1)
- 점포 점포수 계열: 구 `점포_수` = 신 `전체_점포_수`로 통일. `일반_점포_수` = `전체_점포_수 − 프랜차이즈_점포_수`로 전 분기 역산. `유사_업종_점포_수`는 20261 분기 결측 (H2)

### 0-3. grain 판정 (H4)

컬럼명으로 grain을 정하지 않는다. (a) 파일 경로·이름의 `배후지`/`행정동` 문자열, (b) 공간 코드값이 `영역-상권`(1,650) / `영역-상권배후지`(1,071) / `영역-행정동`(425) 중 어느 집합에 속하는지로 판정한다. 두 신호가 불일치하면 빌드 중단.

- 상권 코드와 배후지 코드는 네임스페이스가 완전히 분리돼 있다(교집합 0). 코드값만으로 구분 가능.
- `추정매출/2025/(추정매출-상권배후지)_2025년.csv`는 컬럼이 `trdar_cd`지만 코드값이 영역-배후지에 속하므로 배후지로 강제 배정한다.

### 0-4. 파일별 인코딩 감지 (M3)

`BOM 확인 → CP949 시도 → UTF-8 폴백`. 단일 인코딩 가정 금지. (임대료 = UTF-8-BOM, 추정매출 2024 배후지 = UTF-8, 나머지 = CP949)

### 0-5. 커버리지 부족은 null 유지 (M2, L1)

`영역-상권` 1,650 대비: 추정매출 1,577(−73), 상주인구 1,637(−13), 직장인구 1,643(−7). 조인은 영역·점포 기준 left join, 없는 값은 `null` + `missing_reason`. **0으로 대체 금지.** 후보 근거에서 해당 차원이 비면 등급을 `조건부 검토` 이하로 내리고 누락을 표시한다.

### 0-6. 임대료는 별도 로더 (M4)

`매장용빌딩 임대료,공실률 및 수익률 통계 데이터.csv`는 2행 헤더 wide 포맷, 권역(`지역별(1)/(2)`) grain, 2021Q1~2025Q4(20261 없음). 언피벗 후 `권역 × 분기 × {임대료, 공실률}` long table로 만든다. 상권 후보에 직접 붙이지 않고 **권역→후보 매핑 테이블**을 경유한다. `투자수익률/소득수익률/자본수익률` 3열은 로드하지 않는다(운영 allowlist 제외).

R-ONE 상권별 임대동향은 `data/임대료/R-ONE_임대동향_분기.csv`에서 읽고, `output/crosswalks/crosswalk_rone_trdar.csv`를 통해 서울시 상권분석 상권에 연결한다. 단, R-ONE과 서울시 상권분석 상권은 동일 경계가 아니므로 이 crosswalk는 명칭·별칭 기반 **proxy**다. `mapping_status=matched`, `mapping_role=primary`, `target_reuse_count=1`, `join_eligible=yes`인 행만 자동 결합 후보로 허용하며, 값은 계속 `spatial_grain=R-ONE 상권`·`grain_is_proxy=true`로 표시한다. `review`·`component`·재사용·`unresolved`는 사람 검토/보류한다.

### 0-6-1. 추정매출 값 수준 계약 (값 수준 QA 2026-09-02, `value-level-qa.md`)

- `당월_매출_금액`은 **해당 분기 합계**(컬럼명 '당월'은 레거시). `rev_per_store`·evidence 단위는 `원/점포·분기`로 표기하고 월 매출로 환산 표시하지 않는다.
- `rev_per_store < ₩30만/분기`(≈₩10만/월)는 카드매출 표본 부족 아티팩트 → **결측 취급**(신호·반대 근거로 쓰지 않고 `missing_features`에 사유 기록).
- **상권×업종 grain 추정매출 커버리지는 53.9%**(상권 단위 전 외식으로는 90%). 카드매출 표본이 임계치 미만인 조합을 추정에서 제외한 구조적 결과. **다른 grain(상권배후지·행정동) 매출로 fallback하지 않는다**(결정 2026-09-02, `value-level-qa.md` 발견 1) — 표본 부족은 "소규모 시장" 신호이고, 넓은 grain으로 채우면 과대평가·tier 인플레이션이 된다. host 상권에 업종 매출이 없으면 `sales_thin_market`으로 판정해 `조건부 검토` 유지 + `counter_evidence`·`missing_features`에 **"추정매출 미제공 — 카드거래 표본이 추정 임계치 미만(소규모 시장 가능성), 매출 검증 불가"**로 기록한다("결측"과 구분).

### 0-7. 상권변화지표 배후지 fallback (계약)

상권변화지표는 상권·행정동만 있다(배후지 버전 없음). 후보가 배후지 grain이면 소속 상권의 지표값으로 fallback하고 `spatial_grain="상권(배후지 대리)"`로 표시한다.

### 0-8. 최신 분기 재확인

feature table 빌드마다 각 데이터의 실제 관측 종료 분기를 다시 계산한다. 2026-09-01 기준: 점포·추정매출·길단위인구·상권변화지표 = 20261, 임대료 = 2025Q4, 상주·직장인구 = 20261 분기코드지만 계단식(값은 연 1~2회 갱신).

## 1. 후보 지점 생성 (2026-09-02 재설계 — 상권 폴리곤 → 지점)

**후보 단위는 상권 폴리곤이 아니라 좌표를 가진 명명된 지점이다.** 상권 폴리곤은 서울의 27%만 덮고(164.9/605.8 km²) 크기 편차가 20배라, 폴리곤을 후보로 내면 (a) 서울 3/4가 후보에서 빠지고 (b) "상권 전체 추천"이 특정 자리 추천이 안 된다. 상권·배후지·행정동은 이제 **지점이 참조하는 배경 지표의 grain**으로만 쓴다.

### 1-0. 지점 seed

| seed | 원천 | 필드 | 이름 예 |
| --- | --- | --- | --- |
| 아파트 단지 | `data/공동주택/아파트단지_서울.csv` | 좌표(X/Y_5181), 세대수, `geocode_신뢰도` | "리센츠아파트 인근" |
| 도시철도역 | `data/도시철도역사/역사정보_서울.csv` | 좌표, 노선, 환승 | "잠실새내역 인근" |

- 아파트는 `geocode_신뢰도 ∈ {high, medium}` 만. `low`·`none`(미매칭 349) 제외.
- 카카오 POI는 **부분 이식된 선택적 seed**다. `data/카카오POI/카카오_로컬_POI_잠실역.csv`는 잠실역 1km·FD6/CE7 샘플(90행)이며, 선택 지역 전체 커버리지를 의미하지 않는다. 원본 `poi_id`·조회시각·검색조건을 보존하고 매물·공실·성공 outcome으로 사용하지 않는다.
- `scripts/ingest_kakao_poi_grid.py`는 선택 경계를 EPSG:5181 격자로 나눠 Kakao `rect`를 조회하고, 프로젝트 폴리곤 PIP·Kakao ID 중복 제거·**45문서** 노출상한 포화 4분할·커버리지 manifest를 남긴다. 출력 `data/카카오POI/context/`은 seed로 자동 로드하지 않는다. `recommendation_pipeline.py --include-poi-context`는 요청과 정확히 일치하는 `complete_requested_queries` snapshot만 후보별 250m·500m RAG 관측값으로 집계한다. 이 값은 지점 grain의 상세 맥락이며 **지역 특성 FC를 새로 만들지 않고, 좋은 입지 판정·정렬·긍정/반대 근거를 바꾸지 않는다.** `coverage`는 입력 카테고리/키워드의 관측 완결성일 뿐이다. 경계·상권/배후지/행정동 겹침의 정본은 SHP PIP이며, Kakao 결과는 이를 대체하지 않는다.
- **격자 합성 후보 seed (2026-09-02)**: 개별 상가 매물 크롤링은 불법·비확장이므로, 대신 지역을 격자(`--grid-spacing-m` 기본 100m)로 나눈 **합성 좌표**에 공개 데이터 파생 접근성/경쟁 맥락을 붙인 **`project_generated` 근거 레코드**를 만든다(`scripts/generate_gridpoint_evidence.py` → `output/generated_evidence/<slug>/`, 스키마 `artifacts/20-method/generated-evidence-schema.json`, 감사 `generated-gridpoint-seed-audit.md`). **개별 상가·매물 데이터가 아니다** — 주소·면적·월세·주차·공실·매물 링크 없음. 매물 데이터 공백은 이걸로 메워지지 않는다.
  - 절차: 격자 PIP → **반경 150m 내 영업 중 음식점 인허가 ≥3** 상업 필터 → 역·아파트 seed 80m dedup → **최원점 표본추출**로 지역별 지리적으로 퍼진 `--per-region-limit`(기본 10)개.
  - `--all-seoul`: 서울 25개 자치구 전체를 각각 ~10개 생성 + `output/generated_evidence/_seoul_index.json`. (2026-09-02 실행: 250 레코드, schema 0)
  - `metrics`는 반경 500m 역·버스·아파트 + **10개 외식 업종별 영업 중 인허가 수 전부**(특정 업종 하드코딩 금지). `generator.params.industries`에 업종 범위·필터 근거 기록.
  - 이 좌표는 **실제 매물·점포가 아니다.** 후보로 쓸 때 `candidate_type=생성지점_격자`, `synthetic_anchor=true`, `spatial_grain=지점(생성)`, `precision=지점(생성)`, `listing_url·address_point=null`을 강제하고, `place_name`을 "…(격자 생성 좌표 · 실제 매물·점포 아님)"으로, `context_notes[0]`에 생성 사실·연결된 `evidence_id`를 명시한다.
  - **tier 캡**: `synthetic_anchor=true` 후보는 `추천` 상한을 `조건부 검토`로 캡한다(실제 임대 가능 호실 미확인). 반대근거에 사유를 기록한다.
  - `recommendation_pipeline.py --include-generated-points <seeds.json|dir>`로 기존 seed에 **추가**한다(대체 아님). `seeds.json` + `gridpoint_evidence.jsonl`을 함께 읽어, 합성 후보 evidence에 **반경 500m 인허가 경쟁 metric**(요청 업종 + 전체 음식점, `source=data/인허가/음식점_인허가_서울.csv`)과 `context_notes`에 10개 업종 브레이크다운을 연결한다. 이 metric은 경쟁 규모 맥락이며 `fit_tier`·정렬 미반영(§9-1 '신호 없음'). 역·버스·아파트는 파이프라인이 실행 시점에 재계산한다. `--limit`로 자를 때 앵커 타입(아파트/역/생성지점)이 id 정렬 편향으로 통째로 잘리지 않도록 **같은 tier 안에서 타입 라운드로빈 인터리브** 후 절단한다(§5).
- 향후 seed 확장(추가 이식 시): 상가·근생 POI(카카오/네이버 지도), 지하철 출구 좌표, 검증된 매물.

### 1-1. 생성 절차

1. 시도·시군구·(선택)행정동 경계를 확정한다.
2. 경계 **내부 + 경계에서 300m 이내**의 seed 지점을 모은다(경계 바로 밖 대단지·역도 실질 후보).
3. 두 지점이 **80m 이내**면 병합한다(역과 붙은 단지 → 한 지점, 이름은 둘 다 표기).
4. 각 지점에 배경 grain을 부착한다:
   - **포함 상권**: `영역-상권` point-in-polygon. 없으면 **최근접 상권**(거리 기록) — 300m 초과면 상권 미부착.
   - **포함 행정동**: `영역-행정동`(서울 전역) point-in-polygon. 항상 부착.
   - **포함/최근접 상권배후지**: `영역-상권배후지`.
5. 대상 업종 점포 0 지점도 `greenfield=true`로 유지한다.
6. 한 경계에 지점이 과다하면(예: 한 동 아파트 40개) 세대수·유동밀도 상위로 축소하되 억지로 3~5개를 채우지 않는다.

### 1-2. 지표별 grain 선택 (지점 → 배경값)

지점에 붙이는 각 FC feature는 **가장 세밀하게 계산 가능한 grain 하나**만 쓴다. "상권·배후지·행정동 동일 지표 동시 투입 금지"(data-usage-classification) 유지.

| FC feature | 지점에서 쓰는 grain | 프록시 여부 |
| --- | --- | --- |
| FC-07 역·버스, FC-08 아파트 | **지점 반경 250~500m 직접 계산** (원천 좌표 보유) | 아님 — 지점 고유값 |
| FC-01 유동밀도, FC-02, FC-03·04 인구, FC-05, FC-11 변화, FC-30·31·32 업종, FC-12, FC-40, FC-50 | 포함 상권 → 없으면 **행정동** (`영역-*-행정동` CSV) | 포함 상권의 centroid가 아니면 `grain_is_proxy=true`·거리 기록. 행정동 대리면 `grain_is_proxy=true`·`proxy_note="행정동 배경값"` |
| FC-06a·b 외국인 | 포함 행정동 (원 grain) | 지점≠행정동 centroid → `grain_is_proxy=true` |
| FC-20·21 임대료·공실, FC-41·53 | 권역 / 자치구 | 기존대로 `grain_is_proxy=true` |
| FC-42, FC-52 | 서울시 / 자치구 | 기존대로 |

- 업종 데이터(FC-30·31·32·12): 포함 상권에 대상 업종 행이 있으면 상권×업종, 없으면 **행정동×업종**(`점포-행정동.csv`·`추정매출-행정동.csv`). 둘 다 없으면 해당 차원 null + `greenfield`.
- FC-11 상권변화지표: 포함 상권 라벨 → 없으면 행정동 라벨(`상권변화지표-행정동.csv`). 배후지 버전은 없음.

## 1-3. 명명된 위치 출력

출력은 상권 코드가 아니라 **시 > 구 > 동 > 앵커(지점명) > 좌표 > 참조 상권**이다.

| 필드 | 값 | 원천 |
| --- | --- | --- |
| `anchor` | `{name, type: 아파트단지\|역\|카카오POI, distance_m: 0, households/line}` | seed 지점 |
| `place_name` | "리센츠아파트 인근", "잠실새내역 인근" (앵커명 + "인근") | seed |
| `sido`/`sigungu`/`admin_dong` | 지점 포함 행정동 (`영역-행정동`) | point-in-polygon |
| `point` | 지점 좌표 `{x, y, crs: EPSG:5181}` | seed |
| `host_commercial_area` | `{code, name, relation: 포함\|최근접, distance_m}` — 지점이 참조한 상권 | §1-1.4 |
| `overlapping_units` | 지점이 속한 상권·배후지·행정동 코드 | crosswalk / PIP |
| `nearby_anchors` | 지점 반경 500m 내 다른 역·단지 (본 앵커 외) | 반경 계산 |
| `address_point` | 매물·역지오코딩 확보 시만 | 이식 슬롯 |
| `precision` | `지점` (기본, 앵커 좌표 ±수십 m) / `매물주소` (매물 확보 시) / `행정동`·`상권` (seed 없어 fallback) | — |

- **`precision` enum = `지점` / `매물주소` / `상권` / `행정동`.** `지점`이 기본. `상권`·`행정동`은 seed 0개로 fallback한 후보만. (구) `상권+앵커`는 폐기.
- 아파트 앵커: K-apt 등록 단지만(소형 빌라·연립 누락). 좌표는 VWorld 지오코딩(신뢰도 등급 동반). **동·호수, 정확한 상가 호실, 매물 월세 생성 금지**(F16·F18).
- 역 앵커: 역 좌표까지만. **출구 번호 생성 금지**(F16).
- `place_name`은 "인근"으로 끝낸다 — 앵커 = 방향 기준점이지 그 자리 자체가 아님.

## 2. 하드 조건

- 선택 지역(경계 + 300m) 밖 지점 제외
- 업종 코드가 10개 표준(CS100001~CS100010) 밖이면 실행 중단
- seed 지점이 0개면(경계 내·인접에 아파트·역·검증된 POI 없음) 중단하고 "이 범위에 지점 seed 없음 — POI·매물 이식 필요" 반환
- 아파트 seed는 `geocode_신뢰도 ∈ {high, medium}` 만
- 실제 매물 데이터가 있을 때만 월세·보증금·면적·주차 조건으로 필터. 없으면 지점 후보 유지 + 해당 조건 `unsupported`
- **feature table 빌드가 0절 규칙을 통과하지 못하면 후보 생성 중단, 원인 반환**
- 업종 지표(점포·추정매출)가 상권·행정동 어느 grain에서도 안 붙는 지점은 `greenfield` + 시장수용 근거 부족 표시

## 3. 근거 차원

지역 특성값은 `artifacts/10-analysis/regional-characteristics-profile.md`의 feature(FC id)에서 가져온다. 이 절은 그 feature를 metric-contract의 7개 차원에 매핑하고 후보 카드에서 어떻게 쓸지만 정의한다. 원 지표 정의·계산식·status는 프로파일이 정본이다.

**후보가 지점(§1)이므로**: FC-07·08은 지점 반경 직접 계산(고유값), 나머지는 §1-2 표대로 포함 상권 → 행정동 배경값(`grain_is_proxy` 표기). 아래 표의 "결합 주의"에 지점 프록시 규칙을 추가한다.

**설명력 검증(2026-09-02, `feature-evidential-value.md`)**: 서울 전체 상권×업종에서 **연속 FC 중 폐업/생존에 단조 신호(|ρ|≥0.25)를 가진 것은 0개**. 전체 FC 합산도 churn rank R² +6%p. → **피처 가중합 스코어(`fit_index_v1` 학습형) 금지**, 등급은 하드조건·근거 유무·반대근거로만(§4~5). FC별 신호 등급은 프로파일 §9-1:
- **범주 신호**(FC-10 등급·FC-11 라벨): 지역 배경 리스크 · 반대근거 1항목. 연속 risk 점수는 순위 근거 금지.

- **모멘텀 신호 ≠ 품질**(FC-32·12): "시장 성장/축소" 맥락으로만, 신규 진입 유불리로 단정 금지.

### 3-1. feature status 처리

- `active`: 정상 사용
- `partial`: 사용하되 후보 카드 `limitation`에 grain·갱신 제약 명시, 데이터 신뢰도 1단계 하향 검토
- `inactive`: 값 대체 금지. `missing_features`에 `{feature, reason}` 추가. 해당 차원에 다른 근거가 없으면 등급 상한 `조건부 검토`

### 3-2. 특성과 판정의 경계

프로파일 feature는 업종·조건과 무관한 서술값이다. "좋은 입지" 판정은 이 절에서만 일어난다:

- (a) 사용자 업종으로 FC-30~32·FC-31을 해당 업종에 대해 계산
- (b) 사용자 특별조건 중 **데이터로 대조 가능한 것만** 반영:
  - 예산 → FC-20·21 (권역 근사, 개별 매물 아님)
  - 고객층·영업시간 → FC-03·04·05 + 유동인구 시간대·연령·성별 구성
  - **면적·주차·층·상세 월세·보증금 → 대조 불가.** `input-and-condition-contract`의 `unsupported_conditions`로 보내고 결과 카드에 "미검증"으로 표시 (매물 데이터 필요)
- (c) 4·5절 등급·순서 규칙 적용

## 4. 등급

- 추천: 필수조건 충족, 수요와 진입의 독립 근거가 있고 치명적 반대 근거 없음
- 조건부 검토: 장점은 있으나 비용·경쟁·최신성·누락 중 하나가 큼
- 주의: 필수조건 불충족 또는 폐업·비용·품질 위험이 큼

구체 임계값은 초기 데이터 분포와 사용자 검증 전까지 `사람 승인 필요`다. 운영 초기에는 분위수 컷을 고정하지 않고 차원별 근거를 보여준 뒤 사용자 피드백을 수집한다.

### 4-1. 근거 3분류 (2026-09-02 검증 반영, `scripts/recommendation_pipeline.py`·`sample_jamsil_coffee.py`)

FC 신호 등급표(프로파일 §9-1)를 판정 로직에 고정한다. 후보마다 관측값을 아래 셋 중 하나에 넣는다.

| 버킷 | 필드 | 판정·정렬 반영 | 담기는 FC |
| --- | --- | --- | --- |
| 긍정 근거 | `reasons` | O | 약한 배경 신호(FC-08 배후주거, FC-31 매출규모, FC-07 bus_n)만. **각 항목에 "약한 배경 신호" 표기.** |
| 반대 근거 | `counter_evidence` | O | 범주 신호(FC-10 등급 주의·경계, FC-11 라벨 HH/HL) · 하드조건 미충족 · 핵심 데이터 결측 |
| 배경 서술 | `context_notes` | **X** | 신호 없음(FC-01 유동밀도, FC-30 점포밀도, FC-07 역거리 등) · 모멘텀(FC-32 프랜차이즈) |

- **약한 배경 신호는 단독 추천 승격 금지** — `reasons` 2개 이상 + 반대근거(blocking) 없음일 때만 `추천`. 1개거나 없으면 `조건부 검토`.
- 약한 배경 신호가 긍정 근거의 전부이면 `data_confidence`를 하향하고 그 사유를 명시한다("검증된 품질 신호 아님").
- `context_notes`의 값은 `fit_tier`·정렬 키·`data_confidence`에 절대 반영하지 않는다. 사용자 카드에는 중립 서술로만 노출한다. FC-42 업종 검색 관심도도 최신 원계열·계절 국면·미검증 급등 여부만 이곳에 둔다.

## 5. 표시 순서

동일 등급 안에서 다음 순서로 비교한다.

1. 반대 근거 수 (적은 순)
2. 데이터 신뢰도
3. `candidate_id` (안정 정렬)

**검증된 품질 신호가 없으므로 "긍정 근거 수"로 등수를 매기지 않는다** (`-len(reasons)` 정렬 키 제거, 2026-09-02). 긍정 근거는 등급 승격 여부에만 쓰고, 같은 등급 안 순서는 반대 근거·신뢰도로만 가른다.

**타입 인터리브 (2026-09-02)**: 같은 tier 안에서는 `candidate_type`(아파트단지_인근·역_인근·생성지점_격자·카카오POI_인근)을 라운드로빈으로 섞은 뒤 `--limit`로 자른다. id 문자열 정렬(APT<GEN<POI<STN)이 한 타입을 통째로 잘라내는 편향을 막는다. 각 타입 안 순서는 위 1~3 그대로.

화면에는 기본 3~5개를 보여주되 후보가 부족하면 수를 억지로 채우지 않는다.

## 6. 선택적 내부 지수

`fit_index_v1`은 UX 정렬이 꼭 필요할 때만 사용한다.

- 예측 확률이 아니다.
- `score_is_predictive=false`를 반환한다.
- 산식과 버전을 공개한다.
- 누락값을 자동 50점으로 대체하지 않는다.
- 진입환경 성분은 프로파일 FC-10 `entry_health_v1`을 그대로 사용한다(산식·컷 확정 2026-09-02, `regional-characteristics-profile.md` 7절, `entry-health-v1-cut-design.md`). **전 업종 통합 지역(상권/행정동) 배경 등급 — 업종 구분 없음.** 공실률 매칭 여부에 따라 `core`/`enriched` 변형이 갈리며(현재 전부 `core`), 후보 카드에 어느 변형인지 표기한다.
- 등급은 판정에서 **반대근거 1항목**으로만 쓴다(주의·경계일 때). `fit_tier` 게이트·정렬키로 승격 금지. 산식·컷·입력 분위 4개(폐업률·개업률·점포증감률·라벨리스크) 항상 노출. `score_is_predictive=false`.

`entry_health_v1` 가중치·컷은 확정(2026-09-02 승인). `fit_index_v1` 가중치는 여전히 미확정이며 사람 승인이 필요하다.

## 8. 실패·fallback

- feature table 빌드 실패(0절): 후보 생성 중단, 실패한 규칙과 파일 반환
- 지점 seed 0개(경계 내·인접에 아파트·역·검증된 POI 없음): 중단, "POI·매물 이식 필요" 반환
- 지점이 어느 상권 폴리곤에도 안 들어가고 최근접 상권도 300m 초과: 업종·유동 지표를 **행정동 배경값**으로, `host_commercial_area=null`, `grain_is_proxy=true`
- 대상 업종 데이터가 상권·행정동 모두 없음: greenfield로 유지, 시장수용 근거 부족 표시
- 추정매출 결측 상권(73개, FC-31 null): 현재 수요 차원 null, 등급 상한 `조건부 검토`

- 프로파일 inactive feature(랜드마크 단일시설, 개별 매물): 항상 `missing_features`에 포함, 해당 차원 다른 근거 없으면 등급 상한 `조건부 검토`
- partial feature 공통(FC-06a·06b·41·42·51·52·53): 원 grain(행정동·자치구·서울시)과 다르면 `grain_is_proxy=true` + `proxy_note`. crosswalk 미경유·프록시 표기 누락 시 반려(F10 계열)

## 9. 버린 대안

- 원천 CSV 직접 조인: 연도 폴더 중복(H1)·스키마 드리프트(H2)로 (분기+공간+업종) 키가 2배가 됨. 정규화 feature table 강제.
- header 이름 기반 로딩: 2025 영문 파일 3개(H3)와 배후지 grain 라벨 오류(H4)에서 조용히 실패. 위치 기반 + rename 사전으로 대체.
- 2026 파일로 2025 분기 덮어쓰기: 스키마가 달라(전체/일반 vs 점포/유사업종) 분기 간 피처 불연속 발생. 분기-파일 1:1 배정으로 대체.
- **상권 폴리곤을 후보 단위로 사용**(초기 설계): 서울 27%만 커버, 폴리곤 크기 20배 편차 → "상권 전체 추천"이 특정 자리 아님. 2026-09-02 지점(아파트·역) 후보로 교체. 상권은 배경 지표 grain으로 강등.
- 격자(그리드) 후보: 서울 전역 균일 커버는 되나 "@@동 @@블록"처럼 이름이 없어 직관성 낮음. 앵커(아파트·역) seed 우선, 격자는 추후 보조.
