# 팀 공유용 데이터 스키마

버전: v1.1
기준일: 2026-09-03
작성: GPT(Codex)

이 문서는 서울 창업 입지 추천 프로젝트의 데이터를 팀원이 같은 의미로 이해하고 사용할 수 있도록 만든 데이터 사전이다. 파일명만 나열하지 않고, 각 데이터의 공간 단위(grain), 기간, 키, 출처, 추천 사용 범위와 한계를 함께 정의한다.

세부 구현 계약은 [`artifacts/10-analysis/data-schema.md`](../artifacts/10-analysis/data-schema.md), 기계 판독용 레지스트리는 [`artifacts/10-analysis/data-schema.json`](../artifacts/10-analysis/data-schema.json)에서 확인한다.

테이블·주요 컬럼·PK/FK 관계를 그림처럼 확인하려면 [`데이터베이스 ERD`](architecture/data-schema-erd.md)를 참고한다. ERD는 실제 DDL을 기준으로 작성했으며 공간 코드 기반의 논리 결합과 실제 DB FK를 구분한다.

PostgreSQL + PostGIS로 이식할 때의 테이블 구조와 실행 순서는 [`postgres-migration-plan.md`](postgres-migration-plan.md)와 [`db/001_location_schema.sql`](../db/001_location_schema.sql)을 참고한다.

현재 로컬 PostgreSQL 18.4의 프로젝트 DB `ideaton`과 Docker 팀 공유 DB에 이 논리 스키마의 물리 테이블이 적재되어 있다. `location.store_quarter`·`sales_quarter`·`flow_quarter`는 2021~2026 분기를 보존하고, `location.permitted_establishment`는 공공 인허가 원본을 운영 점포의 대체값이 아닌 감사·경쟁 규모 맥락으로 보존한다. 추천 파이프라인의 기본 읽기 저장소는 아직 기존 Parquet/DuckDB snapshot이다.

### 저장소·실행 환경 계약

| 구분 | 접속 정보 | 역할 | 상태·주의 |
| --- | --- | --- | --- |
| 로컬 원본 | Postgres.app `127.0.0.1:5432/ideaton`, 사용자 `parkjunwoo` | 개인 작업·원본 적재 | PostgreSQL 18.4. 현재 로컬 `trust` 인증으로 비밀번호 없음. 외부 접속용이 아님 |
| 팀 공유 미러 | Docker `<Docker 호스트 LAN/VPN IP>:55432/ideaton`, 사용자 `ideaton` | 팀원 공용 조회·개발 | PostgreSQL 16.14. `postgis`, `vector` 활성화. `ideaton_pgdata` volume에 저장 |

Docker DB는 로컬 원본의 복사본이며 두 DB는 자동 동기화되지 않는다. 팀원은 `127.0.0.1`이나 Postgres.app의 `5432`가 아니라 Docker 호스트 IP와 `55432`를 사용한다. `POSTGRES_PASSWORD`는 `.env.docker`에만 보관하고 문서·Git에 기록하지 않는다. 현재 추천 파이프라인은 두 DB가 아니라 기존 Parquet/DuckDB snapshot을 기본 읽기 저장소로 사용한다.

## 1. 프로젝트에서 데이터가 사용되는 흐름

```text
사용자 입력
  └─ 자치구·행정동·업종·특별조건
       ↓
공간 정본
  └─ 상권·상권배후지·행정동 경계와 코드
       ↓
후보 지점
  └─ 역·아파트·Kakao POI 또는 생성 격자 좌표
       ↓
지역·업종 데이터 결합
  └─ 점포·추정매출·유동인구 + 배경 데이터
       ↓
근거 카드
  └─ 출처·기간·공간 단위·반대 근거·결측을 포함한 RAG Evidence
       ↓
LLM 설명
  └─ 근거에 있는 사실만 자연어로 설명
```

핵심 원칙은 **성공확률을 예측하는 데이터셋이 아니라, 현재 입지의 조건과 근거를 설명하는 데이터셋**이라는 점이다. 과거 매출·점포 수는 관측된 시장 상황이지 특정 후보의 미래 성공 정답이 아니다.

| --- | --- | ---: | --- |
| `commercial_area` | 서울시 상권 | 1,650 | `상권_코드` |

### Evidence 레코드의 공통 필드

모든 근거는 최소한 다음 정보를 가진다.

| 필드 | 의미 |
| --- | --- |
| `metric_name` | 사람이 읽을 수 있는 지표명 |
| `value`, `unit` | 관측값과 단위 |
| `source_type` | 공식 파일·API snapshot·관측 POI·뉴스 메타데이터·파생·생성 |
| `source_path` | 원천 또는 파생 산출물 경로 |
| `source_period` | 값이 관측된 기간 또는 snapshot 기준 |
| `spatial_grain` | 지점·상권·배후지·행정동·자치구·권역·서울시 |
| `grain_is_proxy` | 다른 공간 단위의 대리값인지 여부 |
| `normalizations` | 계산·정규화·변환 내역 |
| `missing_reason` | 값이 없을 때의 사유 |

후보 전체 구조의 정본은 [`rag-evidence-schema.json`](../artifacts/20-method/rag-evidence-schema.json)이다.

## 5. 결합 규칙

### 기본 결합 키

```text
(기준_년분기_코드, 공간단위 코드, 서비스_업종_코드)
```

업종이 없는 데이터는 업종별 데이터에 복제하지 않고 배경값으로 결합한다. 결합 전후 행 수·키 중복률·결측률을 기록한다.

### 공간 결합

1. 상권·배후지·행정동 SHP/CSV가 공간 정본이다.
2. 후보 지점은 PIP로 포함 상권·배후지·행정동을 판정한다.
3. 행정동과 상권이 경계를 걸치면 문자열 라벨이 아니라 면적 crosswalk를 확인한다.
4. R-ONE은 `output/crosswalks/crosswalk_rone_trdar.csv`의 `join_eligible=yes`만 자동 결합한다.
5. 거리 계산은 EPSG:5181에서 수행한다.
6. many-to-many가 생기면 자동 결합을 중단하고 중첩·crosswalk 규칙을 명시한다.

### 결측과 대리값

- 결측을 0으로 바꾸지 않는다.
- 다른 grain의 값은 `grain_is_proxy=true`와 `proxy_note`를 함께 기록한다.
- 데이터가 없다는 이유만으로 후보를 성공·실패로 확정하지 않는다.
- 생성 격자는 `synthetic_anchor=true`, `precision=지점(생성)`, `listing_url=null`, `address_point=null`이다.

## 6. 현재 데이터로 가능한 것과 불가능한 것

### 가능한 것

- 선택한 자치구·행정동 안에서 업종별 점포·매출·유동인구 비교
- 역·아파트·정류장·POI를 기준으로 한 지점 후보 생성과 주변 맥락 설명
- 상권·배후지·행정동의 중첩 관계와 지역 배경 리스크 표시
- 공식 도시계획·정비사업 snapshot과 뉴스·검색 관심도 context 제공
- 각 주장에 출처·기간·공간 단위를 붙인 근거 기반 추천

### 현재 불가능한 것

- 개별 상가의 보증금·월세·전용면적·권리금·주차·현재 공실
- 실제 임대 가능한 호실의 주소·매물 링크
- SNS 게시물 전수·도달량·감성
- 후보별 미래 성공·수익·손익·생존확률 정답
- 계획 노선의 확정 정거장 위치·배차 간격·출구별 유동
- 소형 빌라·연립까지 포함한 전체 주거 세대

위 항목은 데이터가 생기기 전까지 생성하지 않고 `missing_features` 또는 `unsupported_conditions`로 표시한다.

## 7. 출처와 API 운영 상태

| 출처 | 현재 상태 | 로컬 보존 위치 |
| --- | --- | --- |
| 서울시 상권분석서비스 | 공식 파일 snapshot 이식 | `data/` 핵심 폴더 |
| 국토부 K-apt·공공데이터포털 | API 호출·좌표 보완 후 snapshot | `data/공동주택/` |
| VWorld | 지오코딩·좌표 변환에 사용 | `data/공동주택/`, 캐시 |
| 서울 열린데이터광장·국토부 | 버스·외국인 생활인구 snapshot | 각 `data/` 폴더 |
| 한국부동산원 R-ONE | 표 조회·임대동향 snapshot | `data/임대료/` |
| Kakao Local REST | 잠실 파일럿 snapshot | `data/카카오POI/` |
| Naver DataLab/NCP HUB | 검색 트렌드 snapshot | `data/네이버트렌드/` |
| Naver News API | `서울시 재개발` 수동 snapshot | `data/뉴스/` |
| BigKinds | 사용자 제공 export 정규화 | `data/뉴스/` |
| 도로명주소 좌표제공 API | 배포 URL/IP 확보 전 보류 | `.env.example` 슬롯만 존재 |

API 키 값은 문서·Git에 기록하지 않는다. 추천 실행 시 API를 호출하지 않고 로컬 snapshot을 사용한다. 새 데이터를 가져오면 수집일, 검색어/기간, 행 수, 중복 제거, 커버리지와 manifest를 함께 보존한다.

## 8. 팀 작업 규칙

새 데이터나 컬럼을 추가할 때 다음 6가지를 반드시 기록한다.

1. 무엇을 측정하는가: 지표 정의와 단위
2. 어느 공간 단위인가: 상권·배후지·행정동·자치구·지점
3. 어느 기간인가: 분기·월·반기·snapshot과 실제 수집일
4. 어떤 키로 결합하는가: 기본 키와 crosswalk
5. 추천에서 어디에 쓰는가: 후보 판정·근거 설명·context·audit-only
6. 무엇을 말할 수 없는가: 결측·proxy·커버리지·해석 한계
