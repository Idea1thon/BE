개요

한눈에

시스템은 두 개의 플레인으로 나뉜다. 서빙 플레인은 사용자 요청을 동기로 처리하고, 배치 플레인은 분기마다 서울시 데이터를 재적재해 조회용 번들을 만든다. 두 플레인은 불변 data_version 번들에서만 만난다 — 요청 경로는 원천 데이터를 직접 만지지 않는다.

요청 흐름 (한 문장)

웹 폼(자치구 · 업종 · 특별조건) → API → 입력 정규화·계약 검증 → 후보 상권 선정 엔진(제약 필터 + 근거 차원 분리 + 추천/조건부 검토/주의 등급) → RAG 근거 생성(Evidence JSON + 설명 카드) → 응답 조립(후보 + 추천 근거 + 반대 근거 + 누락 데이터 + 기준 분기 + 공간 단위 + 출처).

확정된 방향

Q-1 후보·폴리곤 규모 = 저장소 실측값 Q-2a 상시 가동 서버 1대 배포 Q-3a 호스티드 LLM, 로컬 모델 불채택 Q-4a entry_health_v1 산식·컷 승인
Q-2b 대상 서버·예산 미정 (self-host 전제) Q-3b LLM 공급자 선정·약관 검토 Q-4b fit_index_v1 가중치 (선택적 정렬값)

Sheet A

시스템 컨텍스트

시스템 경계 안에는 웹 UI·API, 후보/근거/RAG 오케스트레이션, 읽기 저장소, 배치 파이프라인, raw 스냅샷 아카이브가 있다. 경계 밖은 모든 원천 데이터 제공기관과 LLM API다.

Sheet H

불변식 · 반드시 지킬 것

아키텍처가 컴포넌트·응답 계약에 강제하는 규칙. 코드 리뷰·회귀 세트가 이걸 검사한다.

01 · 예측 표현 금지

종합 점수를 신규 점포 "성공 확률"로 부르는 응답 필드를 두지 않는다. 등급은 추천 / 조건부 검토 / 주의, 항상 score_is_predictive=false 동반.

02 · 근거 6요소 필수

후보 응답 계약에 추천 근거 · 반대 근거 · 누락 데이터 · 기준 분기 · 공간 단위 · 출처를 모두 포함한다 (rag-evidence-schema.json required, C6가 게이트).

03 · 계단식 데이터 추세 피처 금지

상주인구 · 직장인구 · K-apt 아파트 · 버스 · 도시철도 스냅샷을 분기 추세·모멘텀 피처로 만드는 파이프라인 단계를 두지 않는다. 수준값만 사용.

04 · 지역 경계 · grain

선택 지역(경계 + 최대 300m 버퍼) 밖 후보를 만드는 코드 경로가 없다. 상권·상권배후지·행정동 동일 지표를 동시에 피처로 투입하지 않는다 (지점당 가장 세밀한 grain 하나).

05 · 임대료 = 권역 통계

임대료·공실률은 시장 권역 / R-ONE 상권 통계이며 개별 매물 조건 저장소로 취급하지 않는다. 권역→후보 매핑을 경유하고 grain_is_proxy=true 표기.
